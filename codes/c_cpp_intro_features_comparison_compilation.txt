SECTION 1 — INTRODUCTION TO C
================================================================================

1) What is C? Give a brief history.
   C is a general-purpose, procedural, statically-typed, compiled programming
   language developed by Dennis Ritchie at Bell Labs between 1969-1973,
   originally to rewrite the UNIX operating system (previously written in
   assembly). It evolved from an earlier language called "B" (itself derived
   from BCPL). C was standardized by ANSI in 1989 (ANSI C / C89) and later by
   ISO (C90, C99, C11, C17, C23). It's often called a "middle-level" language
   because it combines low-level access (pointers, direct memory manipulation,
   bit operations) with high-level constructs (functions, structured control
   flow, expressions).

2) Why is C called a "structured" / "procedural" programming language?
   C code is organized as a sequence of well-defined procedures/functions that
   are called in a controlled, top-down manner using structured control flow
   (if/else, loops, switch) rather than unrestricted jumps (goto-heavy "spaghetti
   code" common in earlier languages like early BASIC/FORTRAN). "Procedural"
   means the program is built around procedures (functions) that operate on
   data passed to them, as opposed to Object-Oriented (where data and behavior
   are bundled into objects) or Functional paradigms.

3) What are the key features of C?
   - Simple and small core language, easy to learn
   - Procedural / structured programming support
   - Rich set of built-in operators (arithmetic, bitwise, logical, etc.)
   - Fast execution — compiles directly to efficient machine code, minimal
     runtime overhead
   - Portable — C programs can run on different platforms with minimal/no
     changes (write once, recompile everywhere)
   - Low-level memory access via pointers — direct control over memory
   - Modular — code can be organized into separate functions/files and
     compiled independently, then linked
   - Rich standard library (I/O, string handling, math functions via stdio.h,
     string.h, math.h, etc.)
   - Extensible — programmers can add their own functions/libraries
   - Statically typed — variable types checked at compile time
   - No built-in garbage collection — manual memory management (malloc/free)

4) Why is C still relevant/widely used today?
   C is the backbone of systems programming: operating system kernels (Linux,
   Windows internals), embedded systems/firmware, device drivers, compilers
   and interpreters for other languages, and performance-critical applications.
   Its close-to-hardware model gives programmers precise control over memory
   and performance with minimal abstraction overhead, which higher-level
   languages can't always match. Nearly every other systems language (C++,
   Rust, Go) either builds on C's ideas or must interoperate with C libraries
   (the "C ABI" is the de facto standard for cross-language linking).

5) What are the limitations of C?
   - No built-in support for Object-Oriented Programming (no classes,
     inheritance, polymorphism natively)
   - No exception handling mechanism (errors handled via return codes/errno)
   - No namespaces — higher risk of naming collisions in large projects
   - Manual memory management — prone to memory leaks, dangling pointers,
     buffer overflows if not handled carefully
   - No function overloading or templates/generics (each function name must
     be unique; no built-in generic programming)
   - Weaker type safety than C++ in some areas (implicit conversions allowed
     more liberally)

SECTION 2 — INTRODUCTION TO C++
================================================================================

6) What is C++? Give a brief history.
   C++ was created by Bjarne Stroustrup at Bell Labs, starting in 1979 as
   "C with Classes," adding object-oriented features to C. It was renamed
   C++ in 1983 (the "++" being a nod to C's increment operator, implying
   "one step beyond C"). It was standardized by ISO starting with C++98,
   followed by major revisions: C++03, C++11 (a landmark "modern C++"
   release), C++14, C++17, C++20, and C++23 — each adding significant new
   features (auto, lambdas, smart pointers, move semantics, concepts,
   modules, coroutines, etc.).

7) What are the key features of C++?
   - Multi-paradigm: supports procedural, object-oriented, generic
     (templates), and to some extent functional programming (lambdas)
   - Object-Oriented Programming: classes, objects, encapsulation,
     inheritance, polymorphism, abstraction
   - Strong type checking (stricter than C in several areas)
   - Function overloading and operator overloading
   - Templates — generic programming (write code once, works for any type)
   - Standard Template Library (STL) — ready-made containers (vector, map,
     set, etc.), algorithms (sort, find, etc.), and iterators
   - Exception handling (try/catch/throw) for robust error management
   - RAII (Resource Acquisition Is Initialization) — ties resource lifetime
     to object lifetime (used heavily with smart pointers)
   - Namespaces — avoids naming collisions in large codebases
   - Backward-compatible with C (most valid C code compiles as C++, with
     some exceptions)
   - Smart pointers (unique_ptr, shared_ptr) for automatic memory management
     without a garbage collector
   - Compiles to native machine code — no runtime VM (unlike Java/C#) —
     giving high performance

8) What are the four pillars of Object-Oriented Programming in C++?
   - Encapsulation: bundling data (members) and methods that operate on it
     within a class, restricting direct access via access specifiers
     (private/protected/public) — hides internal implementation details.
   - Abstraction: exposing only essential features/behavior to the user
     while hiding complex implementation details (e.g. via abstract classes/
     interfaces).
   - Inheritance: a class (derived) can acquire properties and behavior from
     another class (base), enabling code reuse and hierarchical
     relationships.
   - Polymorphism: the ability for objects of different classes to be
     treated through a common interface, with behavior determined at either
     compile time (function/operator overloading — "static polymorphism")
     or runtime (virtual functions — "dynamic polymorphism").

9) What is the difference between a class and an object?
   A class is a user-defined BLUEPRINT/TEMPLATE that defines the properties
   (data members) and behaviors (member functions) that its instances will
   have — it doesn't occupy memory for data until instantiated. An object is
   a concrete INSTANCE of a class — actual memory is allocated, and it holds
   real values for the class's data members. Analogy: "Car" the class is the
   blueprint; "myHondaCity" is an object — one specific car built from that
   blueprint.

SECTION 3 — BENEFITS OF C++ (OVER C, AND IN GENERAL)
================================================================================

10) What are the main benefits/advantages of using C++ over C?
    - Object-Oriented support enables better code organization, reuse
      (via inheritance), and modeling of real-world entities for large,
      complex software systems.
    - The STL provides battle-tested, efficient, ready-to-use data
      structures and algorithms, dramatically reducing development time
      versus hand-writing them in C.
    - Exception handling provides a structured way to detect and respond to
      runtime errors, cleaner than C's manual error-code checking.
    - Templates enable generic, type-safe, reusable code (e.g. one
      std::vector<T> works for any type T), whereas C requires
      duplicating code or using unsafe void* + macros for generics.
    - Stronger compile-time type checking catches more bugs before runtime.
    - RAII + smart pointers reduce memory leaks and dangling pointer bugs
      compared to C's fully manual malloc/free discipline.
    - Operator overloading allows custom types (e.g. a Matrix or Complex
      class) to use natural mathematical syntax (+, *, etc.).
    - Namespaces reduce naming collisions in large, multi-library codebases.
    - Backward compatibility with C means existing C libraries/code can
      still be leveraged.

11) What are the trade-offs / downsides of C++ compared to C?
    - Much larger and more complex language — steeper learning curve, many
      more features/rules to master (templates, multiple inheritance,
      operator overloading corner cases, etc.)
    - Slightly larger compiled binaries and potentially longer compile
      times, especially with heavy template use (template instantiation
      bloat) — though runtime performance is comparable to C when features
      are used carefully.
    - Object-oriented abstraction, if overused, can introduce indirection
      (virtual function calls, vtable lookups) that adds small runtime
      overhead versus C's more direct procedural style — though this is
      usually negligible and avoidable ("zero-overhead principle" is a core
      design goal of C++).
    - More "ways to shoot yourself in the foot" — features like multiple
      inheritance, implicit conversions via constructors, and operator
      overloading can lead to subtle bugs if misused.
    - Some embedded/safety-critical systems (e.g. certain automotive/
      aerospace standards) restrict or disallow parts of C++ (exceptions,
      RTTI, dynamic allocation) for determinism/certification reasons,
      making pure C sometimes preferred there.

13) Is C++ a strict superset of C? Can you compile C code with a C++
    compiler?
    C++ is often loosely called "a superset of C," but this is NOT strictly
    true — there are subtle incompatibilities. Examples: in C, you can
    implicitly convert void* to any pointer type without a cast; in C++ this
    requires an explicit cast. In C, a function declared as `int foo();`
    means "takes unspecified arguments"; in C++ it strictly means "takes no
    arguments." C allows a variable named the same as a struct tag without
    the 'struct' keyword sometimes differently than C++. So most, but not
    all, valid C programs compile unmodified as valid C++.

14) Why doesn't C support function overloading, but C++ does?
    Function overloading (same function name, different parameter lists)
    requires the compiler to encode extra information (parameter types) into
    each function's internal symbol name so the linker can distinguish them
    — this technique is called "name mangling," which C++ compilers
    implement. C compilers do NOT mangle names (a C function `foo` is
    exported simply as the symbol `foo`), so the linker has no way to
    distinguish multiple functions with the same name but different
    signatures — hence C has no overloading support at the language level.

15) Why does C++ use "cin/cout" while C uses "scanf/printf"? What's the
    real difference?
    cin/cout (from <iostream>) are TYPE-SAFE, operator-overloaded stream
    objects — the compiler automatically determines how to read/write based
    on the variable's actual type (via overloaded << and >> operators), so
    there's no risk of a format-specifier/type mismatch (e.g. accidentally
    using %d for a double). scanf/printf (from <stdio.h>) rely on the
    programmer manually specifying format specifiers (%d, %f, %s, etc.) that
    must exactly match the arguments' types — mismatches compile without
    error but cause undefined behavior at runtime. C++ can still use
    printf/scanf if desired (backward compatibility), but cin/cout is the
    idiomatic, safer C++ approach.

SECTION 5 — COMPILATION STAGES (DETAILED)
================================================================================

16) What are the 4 main stages of C/C++ compilation? Explain each in
    detail.
    STAGE 1 — PREPROCESSING:
      The preprocessor handles all lines starting with '#' before real
      compilation begins. It performs: macro expansion (#define), header
      file inclusion (#include — literally pastes the file's contents in),
      conditional compilation (#ifdef/#ifndef/#endif), and removes comments.
      Output: a single expanded "translation unit" (still human-readable
      C/C++ code), typically viewable via `gcc -E file.c`.

    STAGE 2 — COMPILATION:
      The compiler proper takes the preprocessed translation unit and:
      (a) performs lexical analysis (tokenizing the source into keywords,
          identifiers, literals, operators),
      (b) performs syntax analysis / parsing (building an Abstract Syntax
          Tree, checking grammar rules),
      (c) performs semantic analysis (type checking, scope resolution),
      (d) generates intermediate representation and then optimizes it,
      (e) finally emits ASSEMBLY code (human-readable, architecture-specific
          mnemonics) — viewable via `gcc -S file.c` producing file.s.

    STAGE 3 — ASSEMBLY:
      The assembler converts the human-readable assembly code into machine
      code, producing an OBJECT FILE (.o / .obj). This file contains
      machine instructions but has UNRESOLVED references to any symbols
      (functions/variables) defined in OTHER files or libraries — it is not
      yet executable. Viewable via `gcc -c file.c` producing file.o.

    STAGE 4 — LINKING:
      The linker combines one or more object files together with any
      required libraries (static .a/.lib or dynamic .so/.dll) and resolves
      all the unresolved symbol references from Stage 3, producing the
      final EXECUTABLE file. If a symbol is declared (e.g. via extern) but
      never actually defined anywhere, this stage fails with an "undefined
      reference" / "unresolved external symbol" LINKER ERROR (distinct from
      a compiler error).

    (Optional Stage 5 — LOADING: not part of "compilation" itself, but the
    OS loader subsequently loads the executable into memory, resolves any
    dynamic library dependencies at runtime, and transfers control to the
    program's entry point to begin execution.)

17) What is the difference between a compiler error and a linker error?
    Give simple examples.
    A COMPILER error occurs during Stage 2 (compilation) — caused by
    invalid syntax, type mismatches, or undeclared identifiers within a
    single translation unit. Example: forgetting a semicolon, or calling a
    function that was never declared anywhere the compiler can see.
    A LINKER error occurs during Stage 4 (linking) — the code is
    syntactically/semantically valid and compiles fine, but the linker
    cannot find the actual DEFINITION of a symbol that was declared.
    Example: declaring `extern int x;` or `void foo();` but never actually
    defining x or foo() in any file being linked — produces "undefined
    reference to `foo()`" at link time, not at compile time.

18) What is the difference between a static library and a dynamic
    (shared) library, in the context of linking?
    A STATIC library (.a on Linux/macOS, .lib on Windows) is copied
    directly INTO the final executable at link time — the executable
    becomes self-contained (larger file size) and doesn't need the library
    present at runtime, but every program using it duplicates that code and
    must be RE-LINKED if the library is updated.
    A DYNAMIC/SHARED library (.so on Linux, .dylib on macOS, .dll on
    Windows) is NOT copied into the executable; instead, the executable
    just records a reference to it, and the actual library code is loaded
    into memory at RUNTIME (by the OS loader), potentially shared across
    multiple running programs simultaneously (saving memory), and can be
    updated independently without recompiling the program (as long as the
    interface/ABI doesn't change).

19) What is a translation unit?
    A translation unit is the actual unit of input the compiler processes
    in Stage 2 — it consists of one source (.c/.cpp) file AFTER the
    preprocessor has fully expanded all its #include directives and macros
    into it. Each .cpp file is typically compiled independently into its
    own object file (its own translation unit), which is why declarations
    needed across files require headers, and why the "One Definition Rule"
    (ODR) in C++ concerns definitions across translation units.

20) What is the "One Definition Rule" (ODR) in C++?
    The ODR states that any given function, variable, class, or template
    must have EXACTLY ONE definition across the entire program (across all
    translation units combined) — though it may be DECLARED many times.
    Violating this (e.g. defining the same non-inline function differently
    in two .cpp files) causes a linker error (multiple/duplicate definition)
    or undefined behavior if the violation isn't caught. This is precisely
    why header guards (or #pragma once) and the extern keyword exist — to
    prevent accidental multiple definitions when headers are included in
    multiple translation units.

SECTION 6 — TRICKY / CURVEBALL QUESTIONS INTERVIEWERS ASK IN REAL TIME
================================================================================

1. "If C++ is a superset of C, why doesn't this valid C code compile as
   C++?"   →  void *p = malloc(10); int *ip = p;
   Tests whether you know C++ requires an EXPLICIT cast for void* to typed
   pointer conversions (int *ip = (int*)malloc(10);), unlike C which allows
   it implicitly — a classic "superset" myth-buster.

2. "Why can't you overload functions in C, technically, at the linker
   level?"
   → Tests understanding of name mangling (Q14) — not just "C doesn't
   support it," but WHY, mechanically, at the symbol-table/linking level.

3. "Where does the compiler stop and the linker begin — and which one
   catches an 'undefined reference' error?"
   → Tests whether the candidate genuinely understands Stage 2 vs Stage 4
   rather than lumping "build errors" into one bucket (Q17).

4. "A .h file only contains function declarations, no definitions. Will the
   program compile? Will it link?"
   → It will COMPILE fine (declarations are enough for the compiler to
   check calls), but will FAIL TO LINK if the corresponding .cpp defining
   those functions isn't compiled and linked in — testing separation of
   compile vs link stage understanding.

5. "Can a C++ program call a C library function directly? What extra step
   is needed?"
   → Tests knowledge of extern "C" — needed to prevent C++'s name-mangling
   from being applied to a function whose object code was compiled by a C
   compiler (which does not mangle names), so the linker can find the
   correctly-named symbol.

6. "Is `struct` the same in C and C++?"
   → Trick question: in C, a struct can ONLY contain data members (no
   methods, no constructors, no access specifiers, and you must write
   `struct Point p;` — the tag doesn't auto-become a type name). In C++, a
   struct is essentially a class with members public by default — it CAN
   have constructors, methods, inheritance, access specifiers, and `Point p;`
   works directly without the `struct` keyword.

7. "If templates are so useful, why doesn't C have them?"
   → Tests conceptual understanding that templates require the compiler to
   generate specialized code per type at COMPILE TIME (a C++-specific
   compilation model feature) — C's simpler, more direct compilation model
   and lack of this generic-instantiation mechanism is why C uses void* +
   manual casting, or macros, as (unsafe) workarounds instead.

8. "You changed one line in a .cpp file and only that file recompiled, but
   the program still failed to build. Why?"
   → Tests whether the candidate understands the LINK stage runs separately
   AFTER compilation of each changed file, and can fail independently (e.g.
   if the changed function's signature no longer matches a declaration used
   elsewhere) — a very real day-to-day debugging scenario.

9. "Does C++ have a garbage collector like Java? Then how does it manage
   memory automatically at all (e.g. with smart pointers)?"
   → Tests whether the candidate confuses C++'s RAII/smart-pointer
   deterministic destruction (memory freed the instant an object's scope
   ends / its destructor runs) with a TRACING garbage collector (which runs
   periodically and non-deterministically, as in Java/C#) — these are
   fundamentally different mechanisms achieving a similar end-user benefit.

10. "Since C++ is backward-compatible with C, is it always better to just
    write C++ instead of C?"
    → Open-ended judgment question — a good answer weighs C++'s
    productivity/safety benefits against scenarios where pure C is
    preferred: embedded/safety-critical systems with certification
    constraints, kernel code bases (e.g. Linux kernel is deliberately
    C-only), minimal binary size/footprint requirements, or teams
    prioritizing absolute simplicity and predictability over abstraction.

        ↓

        ↓
